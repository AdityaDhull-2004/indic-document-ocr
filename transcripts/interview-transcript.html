Q5. Model and loss: Explain CTC to an interviewer who knows ML but not OCR. What problem does it solve, what is the blank symbol for, and why did you need zero_infinity=True?

Turn 6

I don't know whatCTC means here. could you explain.

Claude's response

CTC is the core of your model, so it's worth getting solid. Here it is from the ground up.

CTC = Connectionist Temporal Classification

It's the loss function your model trains with. Your trainer computes L_CTC(main head) + 0.3 × L_CTC(auxiliary head).

1. The problem it solves

Your CNN + BiLSTM doesn't output a word. It slides across the image and outputs one prediction for every narrow vertical slice:

image width 256 px  →  CNN shrinks width by 4  →  64 slices ("timesteps", T)
each slice outputs a probability over 973 classes

The label is just a string, say 5 characters (U = 5). So you have 64 predictions and 5 correct characters, and nobody has marked which slice belongs to which character. Ordinary cross-entropy needs a target for every slice, so you can't use it here. Hand-labelling character positions for 1.2 million images isn't possible either.

2. The trick: a "blank" class

Add one extra class meaning "no character here". That's why you have 973 classes: 972 characters + 1 blank. To turn 64 slice predictions into text, apply a collapse rule:

merge adjacent repeats, then delete blanks

slices:          म म – – म म – –      ("–" = blank)
merge repeats:   म – म –
delete blanks:   म म       →  "मम"

The blank has two jobs:

  • Filling space. Most slices fall between or inside characters, and blank lets them output nothing.
  • Separating repeated characters. Without a blank in between, म म म म collapses to a single म. Getting "मम" needs at least one blank between the two.

3. The loss

Many different slice sequences collapse to the same word (म म – म, म – – म, – म – म, …). CTC adds up the probability of every sequence that produces the correct label and takes −log of that sum:

loss = −log( Σ P(every path that collapses to the right word) )

So the model never needs to know where each character sits. It just pushes up whatever paths spell the right word, and it learns the positions by itself. The number of paths grows exponentially, so they're never listed one by one. A dynamic-programming algorithm (forward–backward) computes the sum in O(T·U) time.

At inference you use greedy decoding: take the most likely class in each slice, then collapse. You used no language model, so your scores measure only what the model actually sees.

4. Why zero_infinity=True

A label can only be produced if there are enough slices:

T ≥ U + (number of adjacent repeated characters)    ← each repeat needs a blank between

If a crop is too narrow for its label, no path can produce it. Its probability is 0, so its loss is −log 0 = infinity. One infinite loss turns the gradients into NaN and ruins the whole batch. zero_infinity=True sets those losses to zero, so the batch simply skips that sample.

This is also why you chose height 48 instead of 32. Resizing keeps the aspect ratio, so at height 48 every word comes out 1.5× wider, which gives 1.5× more slices. You measured this: the share of training rows that couldn't be learned fell from 1.58% at height 32 to 0.39% at 48, four times fewer.

The 20-second interview version

"My model outputs one prediction per vertical slice of the word, but the label is just a string with no positions. CTC adds a blank class, defines a collapse rule (merge repeats, drop blanks), and the loss is the negative log of the summed probability of every slice-sequence that collapses to the correct label, computed by dynamic programming. The blank both fills gaps and separates double letters. If an image is too narrow to fit its label, the loss is infinite, so I set zero_infinity=True. That same constraint is why I used height 48: more width, more timesteps, 4× fewer unlearnable samples."

Q6. Architecture: Your model is CNN → BiLSTM → linear layer. Why a BiLSTM rather than a Transformer? And why does it need to be bidirectional for Indic scripts in particular?

Turn 8

we are using a BilSTM because we are recognising word by word where the sequence length is tiny and no need of a transformer that uses attention. I don't know why bi-directional was used for indic script in particular.

Claude's response

Rating: 5/10. The LSTM reason is partly right. The "bidirectional" half is a real gap, and it's an easy follow-up for an interviewer, so learn it.

BiLSTM vs Transformer:

  • Your reason holds. Sequences are short (64 timesteps for a 256 px word) and context is local, so you don't need attention across the whole sequence.
  • The stronger reason is model size. At 2.6M parameters, an LSTM's built-in sense of order and locality helps. A Transformer has to learn positional structure from data, which usually takes more data or more parameters.
  • Honesty trap: REPORT.md says "both were implemented; the LSTM wins at this scale." The flag --neck transformer exists, but I found no trained Transformer run anywhere: no history, no checkpoint, no results. RESULTS.md lists it under "Next runs". So don't say "I measured it". Say: "I implemented it as an option but didn't train it head-to-head. I chose the LSTM for its inductive bias at this size, and a 1–2 point difference would be below my measured noise anyway."

Why bidirectional matters for Indic scripts:

In many Indic scripts, the order glyphs are drawn on the page differs from the order the characters are stored in Unicode.

कि  ("ki")   stored as:  क  then  ि        (consonant, then vowel sign)
             drawn as:   ि  then  क        (vowel sign appears on the LEFT)

CTC emits characters in left-to-right time order. So at the leftmost slice, where the model sees the ि glyph, it must already output क, which is a consonant it hasn't reached yet. A forward-only LSTM at that point has seen nothing to its right. The backward LSTM brings in context from the right, so each slice knows what comes after it.

This happens across your nine scripts:

  • Devanagari, Bengali, Odia: vowel signs drawn to the left (ि, ে, େ)
  • Tamil, Malayalam: vowel signs drawn to the left, and some split vowels that wrap around the consonant, with one part on each side (ொ, ൊ)
  • Devanagari reph: र् is stored first in धर्म but drawn as a hook on top of the next consonant, so here the problem runs the other way

20-second version:

"In Indic scripts, visual order and Unicode order often differ. In कि the vowel sign is drawn left of the consonant but stored after it. CTC emits left to right, so the model must output the consonant before it has visually reached it. The backward pass of the BiLSTM supplies that right-side context."
